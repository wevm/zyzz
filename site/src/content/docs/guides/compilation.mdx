# Build & Delivery

Compile matching code and CSS, publish library artifacts, and deliver styles with server-rendered content.

## Overview

Zyzz compiles style definitions ahead of time. The build emits executable style functions and a matching stylesheet. During rendering, those functions select classes and bind values to inline variables without generating or inserting CSS rules.

For application setup, follow [Getting Started](/docs/introduction/getting-started). Vite and Next.js integrations handle source transformation and CSS delivery. Use the CLI or compiler APIs for standalone builds and library publishing.

Run the CLI from a project with Zyzz installed. `build` compiles `src` into `dist` once. `dev` builds immediately and watches for changes. Failed rebuilds retain the last successful artifacts and recover after valid edits.

```sh
npx zyzz build
npx zyzz dev
```

## Walkthrough

These steps take the `dist` output of the Overview commands to a styled document.

<Steps>

### Inspect the Output

The output includes a complete stylesheet and per-module artifacts. Code and CSS source maps accompany their artifacts.

- **`button.ts`:** The rewritten module for downstream TypeScript lowering.
- **`button.ts.css`:** Styles belonging to that module.
- **`button.ts.zyzz.json`:** Compiler metadata for sources that link the module's contracts.
- **`zyzz.shared.css`:** Shared contributions and responsive variable defaults.
- **`zyzz.css`:** Shared CSS and module styles combined in dependency order.
- **`zyzz.js`:** A script that initializes configurations with saved theme and scheme selections. Projects without configuration initialization do not emit it.

### Bundle the Modules

Keep component imports pointed at authored source. Configure the downstream build to consume the rewritten tree, lower TypeScript and JSX, and bundle the application. Zyzz does not generate declarations or an application bundle.

### Load the Styles

With the default output directory served at `/dist`, load the complete stylesheet once. For configured projects, load the initialization script as a classic script at the start of the document's `<head>` to restore saved selections before paint.

```html title="Document head"
<script src="/dist/zyzz.js"></script>
<link rel="stylesheet" href="/dist/zyzz.css" />
```

Adjust URLs to the deployed asset locations. `dist` is a compiler output directory, not a required public URL. Use `--script public/zyzz.js` when a bundler serves and copies a public directory.

If loading individual module stylesheets, load `zyzz.shared.css` first and retain dependency order. Load either the complete stylesheet or the split stylesheets to avoid duplicate rules.

</Steps>

## Recipes

### Set Build Options

For a different source directory or output location, set the paths explicitly. Keep the package identity stable between builds.

```sh
npx zyzz build src --out-dir build/styles --package-id my-library --minify
```

`--minify` minifies CSS. The CLI preserves browser syntax without compatibility targets. The [Host API](https://github.com/wevm/zyzz/blob/main/docs/api/node/Host/create.md#optionscsstargets) accepts explicit CSS targets for a custom pipeline, which do not polyfill unsupported features.

See the [CLI reference](https://github.com/wevm/zyzz/blob/main/docs/api/cli.md) for flags, structured output, and output ownership.

### Build Libraries

Compile the library's source tree before packaging. A filesystem host provides the same build lifecycle programmatically.

```ts title="scripts/build-styles.ts"
import { Host } from 'zyzz/node'

await using host = await Host.create({
  outDir: 'dist',
  packageId: 'my-library',
  root: 'src',
})

await host.build()
```

The host returns `build`, `watch`, and `close` operations. `await using` releases the output lock when the scope exits, including after an error. Keep a watching host alive for the intended watch lifetime.

Keep generated output separate from owned source files. The host locks each output directory to one active writer and rejects output inside the source root. Its cleanup preserves unrelated files and removes only unchanged owned artifacts.

### Publish Libraries

Before publishing a compiled library:

1. Lower the rewritten TypeScript and JSX with the library's build tools and generate declarations.
2. Export the compiled modules and stylesheet through the package's export map.
3. Include matching code, CSS, compiler metadata, and source maps from the same build.
4. Document the stylesheet import that consumers must load once.

Consumers do not need Zyzz compilation for already-transformed library code. If other Zyzz sources need to link exported styles or themes, retain the generated `<entry>.zyzz.json` contract beside each published entry module. When lowering `button.ts` to `button.js`, keep the adjacent contract at `button.js.zyzz.json`.

The CLI and file host resolve installed package exports and adjacent contracts without executing dependency code. Resolution uses Node import conditions. TypeScript path aliases and browser or native resolver conditions are not inferred. Packed external asset copying remains unsupported.

### Library Stylesheets

Generated `<entry>.zyzz.json` sidecars retain global contributions, fonts, keyframes, and layer constraints across imports and re-exports. Source maps preserve the original authoring content. Identical contributions emit once, while conflicting copies fail compilation.

Keep referenced assets with the published output. Source assets resolve relative to their owning module. The standalone host copies local source assets into its output tree, and Vite resolves assets through its CSS pipeline.

### Transform Source Modules

For an in-memory integration, use `Transform.compile` to rewrite a module and emit its CSS without executing source or reading files. Pass a stable package-relative `moduleId` for linking and source maps.

```ts title="Transform source"
import { Transform } from 'zyzz/compiler'

const output = Transform.compile({
  moduleId: 'my-library/button.ts',
  source: `import { style } from 'zyzz'

export namespace styles {
  export const button = style({ padding: '1rem' })
}`,
})
```

Bundle `output.code` after TypeScript and JSX lowering, and deliver `output.css` from the same build. Preserve `output.map` and `output.cssMap` through downstream processing. Generated classes use authored bindings and optional config IDs, and consumers apply the exported `styles.button()` props to an element.

`Source.extract` reads definitions but does not rewrite executable calls. For imports across modules or relative URLs in stylesheet contributions, use the filesystem host or a [graph integration](https://github.com/wevm/zyzz/blob/main/docs/api/compiler/Graph/compile.md). A standalone transform rejects relative contribution URLs.

### Compile Literal Data

Use `Css.compile` when a pipeline already has literal style data and needs CSS plus a class map rather than rewritten source modules.

```ts title="Compile literal styles"
import { Style } from 'zyzz'
import { Css } from 'zyzz/web'

const styles = Style.define({
  card: { display: 'flex', padding: '1rem' },
})

const output = Css.compile({ styles })
```

Load `output.css` and apply `output.classes.card` as the element's class name. Publish the stylesheet and class map together. The compiler has no filesystem or browser side effects and does not generate executable style functions.

For themes, pass variable definitions in `vars` and apply the returned scope classes from `output.vars`. See [literal styles](https://github.com/wevm/zyzz/blob/main/docs/api/core/Style/literals.md) and [CSS compilation](https://github.com/wevm/zyzz/blob/main/docs/api/web/Css/compile.md) for the supported inputs and composition rules.

### Keep Authoring Source

CSS-only mode emits stylesheets, CSS maps, and the initialization script while leaving original application modules for the normal build.

```sh
npx zyzz build --css-only
```

In Vite, `zyzz({ compiler: false })` retains automatic CSS delivery with the same [explicit-ID requirements](#assign-explicit-ids). Choose one delivery path for an application.

CSS-only output omits rewritten modules and packed module contracts, so [publish libraries](#publish-libraries) from source-rewriting builds.

### Assign Explicit IDs

Without source rewriting, identity-bearing declarations need explicit IDs. This includes independent variables, empty or referenced styles, dynamic styles, variants, themes, and named stylesheet declarations. Ordinary static styles derive classes from ordered declaration data.

```ts title="styles.ts"
import { style, variable } from 'zyzz'

const accent = variable('color', { id: 'my-library-accent' })

export namespace styles {
  export const card = style({ color: accent, padding: '8px' })
}
```

Apply `styles.card({ vars: accent.set('red') })` to bind a value. Keep IDs within the application or package namespace. Reusing an ID shares an identity, and conflicting definitions are rejected during extraction.

### Server Rendering

Apply compiled style props during server rendering and deliver the matching CSS before styled content paints. The server and client must use the same compiled identities and agree on initial theme, scheme, and variant selections.

```tsx title="Card.tsx"
import { style } from 'zyzz/default'

export function Card() {
  return <article {...styles.card()}>Content</article>
}

namespace styles {
  export const card = style({ padding: 4 })
}
```

A config import binds authoring helpers but does not provide CSS delivery. Include scoped rules and eager global contributions through the integration's output graph. Import global-style modules from an application entry so the bundler can discover them.

A custom renderer or build pipeline needs its own proof of CSS delivery, hydration, streaming, and route splitting. Check [Compatibility](/docs/introduction/compatibility) before relying on a platform feature. Existing checks cover these integrations:

- **Next.js:** The [Next.js integration](https://github.com/wevm/zyzz/blob/main/docs/introduction/next.md) owns Webpack and Turbopack wiring. Packed-consumer tests cover server and client components, styled streaming fallbacks, hydration, and route navigation.
- **Solid and Svelte:** Fixtures verify server rendering and hydration through Vite.
- **React renderers:** Fixtures use esbuild-compiled output.
- **Plain HTML:** Fixtures cover serialized attributes and updates.

### Check Delivery

When styles are missing or server and client output differ:

1. Confirm that a bundler integration, CLI build, or compiler API processes the modules that define styles.
2. Confirm that the browser loads the matching stylesheet at the deployed URL.
3. Check that code and CSS came from the same build with the same package and module identities.
4. Check that shared CSS precedes split module stylesheets and that global-style modules are imported.
5. Compare the server's initial selections with the client's theme, scheme, and variants.

Use [Testing & Troubleshooting](https://github.com/wevm/zyzz/blob/main/docs/guides/testing.md) for further checks and [Linting](https://github.com/wevm/zyzz/blob/main/docs/api/oxlint/README.md) for source diagnostics.
